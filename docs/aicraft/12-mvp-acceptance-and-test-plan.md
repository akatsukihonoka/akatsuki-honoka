# 12. MVPの受け入れ基準とテスト計画

## 12.1 受け入れ基準（Acceptance Criteria）

各項目は自動テストまたは記録可能な手動手順で検証する。**全項目合格**をクローズドベータ開始（＝本番デプロイ承認申請）の条件とする。

### 機能

| ID | 基準 | 検証 |
|---|---|---|
| AC-01 | 新規ユーザーがサインアップ→メール確認→オンボーディング→初回生成まで完了できる | E2E |
| AC-02 | ブランド設定を保存すると新版が作成され、旧版は変更できない | 統合＋RLS |
| AC-03 | 生成ウィザードで案が1–10件提示され、案から本文を生成できる | E2E（LLMモック）＋ステージング実LLMスモーク |
| AC-04 | 生成された全バージョンに品質検査結果（機械検査・AIレビュー・total_score・verdict）が存在する | 統合（DB検査） |
| AC-05 | 不合格時に再生成が行われ、試行は最大3回で、超過時に `needs_attention` になる | 統合（モックで不合格強制） |
| AC-06 | AIレビューが失敗した場合、コンテンツは合格扱いにならず `needs_attention` になる | 統合（障害注入） |
| AC-07 | 主張が1件でも未確認、または critical 未解消（上書きなし）の場合、UIとAPIの両方で承認できない | E2E＋API |
| AC-08 | 承認後に本文を編集すると `draft` に戻り、`approved_version_id` と最新版が一致しない状態で承認済み表示されない | 統合 |
| AC-09 | エクスポートは承認済みコンテンツのみ可能 | API |
| AC-10 | 外部サービスへコンテンツを送信するコードパスが存在しない（MVP） | コードレビュー＋ネットワーク許可リストのテスト |
| AC-11 | バージョン差分表示と任意版の復元ができる | E2E |
| AC-12 | カレンダーで予定日を設定・変更できる | E2E |
| AC-13 | 月次レポートの数値がDB集計と一致する | 統合 |
| AC-14 | Stripe テストモードでトライアル開始→有料化→解約→Webhook反映が正しく行われ、同一イベント再送で二重処理されない | 統合 |
| AC-15 | 月間利用枠を超えると生成が拒否され、UIに理由が表示される | E2E |
| AC-16 | 問い合わせが分類され、条件を満たすFAQ質問のみ自動回答、それ以外は回答案＋`waiting_human` | 統合＋E-support |
| AC-17 | データエクスポートと削除申請ができ、削除は運営承認後に実行される | 統合 |

### 品質

| ID | 基準 | 検証 |
|---|---|---|
| AC-20 | E-core: 合格率 ≥ 80%、平均 total_score ≥ 78 | 評価ハーネス |
| AC-21 | E-adversarial: critical出力 0件 | 評価ハーネス |
| AC-22 | E-claims: 主張抽出 再現率 ≥ 85%、適合率 ≥ 70% | 評価ハーネス |
| AC-23 | E-reviewer: 欠陥検出率 ≥ 90% | 評価ハーネス |
| AC-24 | E-support: 分類精度 ≥ 90%、エスカレーション必須ケースの見逃し 0件 | 評価ハーネス |
| AC-25 | 人間監査（ステージングで30件）とAI判定の合否一致率 ≥ 85% | 手動記録 |
| AC-26 | 生成完了 p95: ブログ < 90秒、SNS < 30秒（ステージング、同時10件） | 計測 |

### セキュリティ・運営

| ID | 基準 | 検証 |
|---|---|---|
| AC-30 | 全 public テーブルで、別テナント・viewer・未認証の不正操作が全て拒否される | pgTAP |
| AC-31 | RLS未有効の public テーブルが0 | CI |
| AC-32 | リポジトリ・ビルド成果物にシークレットが含まれない | スキャン |
| AC-33 | エージェントが許可外ツールを呼ぶと拒否・記録され、実行が停止する | 統合 |
| AC-34 | 承認実行器: payload改ざん・期限切れ・二重実行・エージェント資格での承認が全て拒否される | 統合 |
| AC-35 | 全体日次予算到達で新規生成が自動停止し、再開は運営者操作でのみ可能 | 負荷テスト |
| AC-36 | テナント異常消費で当該テナントのみ停止し、他テナントは影響を受けない | 負荷テスト |
| AC-37 | キルスイッチ（`ai.generation.enabled` 等）OFFで即時に該当機能が停止する | E2E |
| AC-38 | 管理コンソールはMFA未完了の運営者・一般ユーザーで403 | E2E |
| AC-39 | 監査ログに 8.3 の対象操作が全て記録され、ログはUPDATE/DELETEできない | 統合 |
| AC-40 | ステージングへのバックアップ復元訓練が成功し、RTO 4時間以内 | 手動記録 |
| AC-41 | 重大インシデント（SEV1）模擬訓練: 検知→通知→停止→判断の流れが runbook 通りに実施できる | 手動記録 |
| AC-42 | 法務確認（U-15, U-17, U-19, U-21, U-22, U-24）が完了している | 確認記録 |

## 12.2 テスト計画

### テストレベル

| レベル | ツール（候補） | 対象 | 実行 |
|---|---|---|---|
| ユニット | Vitest | 機械検査ルール、スコア計算、状態遷移、予算判定、ハッシュ束縛 | 全PR |
| DB / RLS | pgTAP（Supabase CLI） | RLS、RPC（approve_content等）、トリガ、遷移制約 | 全PR |
| 統合 | Vitest + ローカルSupabase + LLMモック + Stripe テストモード/モック | 生成パイプライン、再生成、Webhook、承認実行器、エージェント許可リスト | 全PR |
| E2E | Playwright | AC-01, 03, 07, 11, 12, 15, 37, 38 等の主要フロー | 全PR（モック）／リリース前（ステージング） |
| 評価回帰 | `evals/` ハーネス（実LLM、開発キー・低予算） | E-* セット | プロンプト/モデル/QA変更PR、週次 |
| 負荷・障害注入 | k6 等（候補）＋モックLLMの遅延/エラー注入 | 予算停止、タイムアウト、再試行、キュー滞留 | リリース前 |
| セキュリティ | シークレットスキャン、依存脆弱性、手動レビュー（RLS・認証・ヘッダ） | 全体 | 全PR／リリース前 |
| 手動 | チェックリスト | 法務表示、文言、アクセシビリティ（axe補助） | リリース前 |

### テストデータ

- 架空の事業者10社分のブランド設定（業種: 美容、整体、税理士、飲食、雑貨EC、フィットネス、学習塾、写真館、工務店、コンサル）。
- 架空ユーザー: テナントA（owner/editor/viewer）、テナントB（owner）、未所属ユーザー、運営者（MFAあり/なし）。
- 実在の個人情報・顧客データは使用しない。
- LLMモックは「合格」「機械検査違反」「AIレビュー不合格」「タイムアウト」「スキーマ不正」「インジェクションに従った出力」を決定的に返せること。

### 品質低下の検出（回帰）

- 評価ベースラインを main 上で保存し、変更PRと比較（7.6）。
- 本番では週次で同一評価サブセットを実行し、モデル提供側の変化による劣化を検出。
- 本番KPI（初回合格率、needs_attention率、承認率、再生成率）を週次で前週比較し、5pt超の悪化で司令塔が通知。

### 合否判定とリリース手順

1. ステージングで 12.1 の全ACを実施し、結果を `docs/releases/<日付>-mvp-acceptance.md` に記録。
2. 未達項目がある場合はリリース不可（例外は人間が理由付きで判断し記録）。
3. 本番デプロイ承認申請（人間）→ 承認後に本番構築・デプロイ（人間操作）。
4. 本番スモークテスト（登録→生成→承認→エクスポート、テストテナントで実施後に削除）。
5. クローズドベータ招待の送信は人間が行う。
